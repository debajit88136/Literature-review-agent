# Autonomous Literature Review Agent

An agentic Python tool that takes a research topic and produces a structured, cited literature review — automatically searching arXiv, screening papers for relevance, reading full texts, extracting structured notes, grouping findings into themes, and surfacing open problems raised by multiple papers.

**Live demo:** https://literature-review-agent-kuf6cshecwa5ces6iglrs3.streamlit.app/

> The demo runs in a shared, rate-limited mode (max 6 papers, 10 runs/day across all visitors). Paste your own free [Google AI Studio](https://aistudio.google.com/) Gemini key in the sidebar to remove these limits.

## What it does

Give it a topic (e.g. "retrieval augmented generation") and it will:

1. Search arXiv for candidate papers (free, no API key needed)
2. Ask an LLM to pick the most relevant papers from titles and abstracts, in a single forced-choice call
3. Download each selected PDF and extract its text (falling back to the abstract if extraction fails for any reason)
4. Ask the LLM to write structured notes per paper — method, key findings, datasets, relation to the topic, stated limitations
5. Ask the LLM to group the papers into themes
6. Ask the LLM to find open problems raised by two or more different papers
7. Assemble everything into a Markdown report, with citations built in code from arXiv metadata (never from the LLM)

All of this is exposed through a Streamlit UI with live progress, a rendered review, and a download button.

## Architecture

```
                    ┌─────────────┐
   topic  ────────► │ arxiv_client│  search arXiv, no key needed
                    └──────┬──────┘
                           │ candidate papers
                    ┌──────▼──────┐
                    │  selection  │  LLM: forced-choice "pick best K"
                    └──────┬──────┘
                           │ selected papers
                    ┌──────▼──────┐
                    │ pdf_reader  │  download + extract text
                    └──────┬──────┘                (falls back to abstract)
                           │ paper content
                    ┌──────▼──────┐
                    │ extraction  │  LLM: structured notes per paper
                    └──────┬──────┘                (validated, aliased P1/P2/...)
                           │ notes
                    ┌──────▼──────┐
                    │  synthesis  │  LLM: theme clustering + cross-paper gaps
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   report    │  plain Python builds the Markdown
                    └──────┬──────┘                (citations from arXiv metadata)
                           │
                    ┌──────▼──────┐
                    │   app.py    │  Streamlit UI
                    └─────────────┘
```

Every stage above `report` and `app.py` that talks to the network or an LLM is isolated behind a narrow interface, so the parsing and validation logic in each module is unit-testable without any real API calls.

## Key design decisions

**Pure functions, isolated network calls.** Parsing and validation logic is separated from anything that touches the network or an LLM. This is what makes 86 offline unit tests possible, using a fake LLM and fake network responses.

**LLM output is treated as untrusted input.** Every LLM response is parsed and validated in code, with a defined fallback if it doesn't match the expected shape. The LLM refers to papers by short aliases (`P1`, `P2`, ...) and the code maps these back to real papers — so the LLM cannot invent, drop, or duplicate a paper in the output.

**Citations never come from the LLM.** All citation text (`author (year). title. arXiv:ID`) is built in code directly from arXiv's own metadata, which removes an entire class of citation-hallucination risk.

**Graceful degradation everywhere.** If one paper's PDF fails to download or parse, the pipeline falls back to its abstract rather than dropping the paper or crashing the run. The pipeline stops early only after 3 consecutive paper failures, treating that as a signal something systemic (not just one bad PDF) is wrong.

**Forced-choice paper selection, not relevance scoring.** An earlier version asked the LLM to score each paper 0–5 for relevance. Smaller models gave almost every paper a 5 (score inflation), which made the score useless for filtering. Replacing this with a single forced-choice call — "pick the best K from this list" — fixed it.

**Results are stored in `st.session_state`.** Streamlit reruns the entire script on every UI interaction, including clicking the download button. Without storing the pipeline result in session state, clicking Download would immediately blank the screen, because the rerun would start from an empty result. This was verified on the live deployment: the review stays visible after clicking Download.

**Demo mode with a visitor-supplied key escape hatch.** When a server-side key is configured (as it is on the live demo), the app runs in a rate-limited "demo mode" — max 6 papers, 10 shared runs/day, one run at a time — protected by `demo_guard.py`. Any visitor can paste their own free Gemini key in the sidebar to remove these limits entirely. This was also verified live: a second run attempted while one is already in progress is refused with a clear message, and the run counter decreases correctly after each demo run.

**A quick key check runs before the real pipeline.** An invalid or missing API key is caught in a few seconds, before any arXiv search or paper download, so a bad key fails fast rather than after minutes of wasted work.

## Known limitations

- **Search is arXiv-only.** This keeps the tool free and key-less, and arXiv has strong coverage of CS/AI/ML/physics/math preprints, but it won't find biology, medicine, or social-science literature well. A natural extension is a `SearchClient` interface (parallel to the existing `LLMClient` interface) so a second free source like Semantic Scholar's API could be added later.
- **Search is keyword-based.** Short forms like "LLM" can miss papers that write out "large language model" instead.
- **Results vary between runs.** LLM sampling and newly published arXiv papers mean two runs on the same topic won't be identical. Each report records the date, model name, and exact arXiv IDs used, so a given report is always reproducible as a record even if a fresh run would differ.
- **Long papers are trimmed** to their first ~20k and last ~10k characters before being sent to the LLM, to control cost and context size. A grounding check confirms that numbers the LLM cites do appear somewhere in the source text, but this only proves the number exists in the text — not that it is correctly attached to the claim the LLM made.
- **Gap-finding relies on the LLM merging similar limitations** across papers. It can occasionally miss a real overlap or over-merge two different problems. A stronger design would have the LLM tag each limitation with a category from a fixed list and let Python do the counting and merging instead.
- **Free-tier LLM quotas can change.** The model name is a configurable setting for exactly this reason.
- **The tool selects on-topic papers, not the most influential ones** — arXiv doesn't expose citation counts, so relevance is judged by content, not by impact.

## Tech stack

Python, Streamlit, Google Gemini (`google-genai`, free tier), arXiv API, PyMuPDF (PDF text extraction), `unittest` for testing.

## Running it locally

```bash
git clone https://github.com/debajit88136/literature-review-agent.git
cd literature-review-agent
pip install -r requirements.txt
```

Create `.streamlit/secrets.toml` (never commit this file — it's already in `.gitignore`):

```toml
GEMINI_API_KEY = "your-key-here"
GEMINI_MODEL = "gemini-3.5-flash-lite"
```

Then run:

```bash
streamlit run app.py
```

## Running the tests

```bash
pytest
```

86 tests run offline against a fake LLM and fake network responses — no API key or internet connection required.

## Possible future improvements

- Add a second free search source (e.g. Semantic Scholar) behind a `SearchClient` interface, mirroring how `LLMClient` already makes the LLM provider swappable.
- Let the user tick/untick which selected papers actually get extracted, before the (slower) extraction stage runs.
- Have the LLM tag each stated limitation with a category from a fixed list, so Python — not the LLM — decides which limitations count as a shared "gap."
- Lower the LLM's sampling temperature for more repeatable results between runs on the same topic.
